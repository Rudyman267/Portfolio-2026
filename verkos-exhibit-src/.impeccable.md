# Impeccable Design Context

## Design Context

### Users

**Primary — Security Drone Pilots**
Operators monitoring live drone feeds in dark operations control rooms, often on night shifts. Fatigue is a real constraint: attention spans are compressed, cognitive load must stay low. The interface must be instantly scannable — information hierarchy has to be obvious at a glance without requiring active reading. Primary device is a large desktop monitor (1920×1080 or larger), used alongside the FlytBase dashboard in a split-screen or multi-monitor setup.

**Secondary — Site Managers & Compliance Officers**
Office-based users reviewing finalized mission reports, incident logs, and compliance exports. Brighter ambient environments, more deliberate usage patterns, less time pressure than pilots — but the same expectation of clarity and professionalism.

**Job to be done:** Know what's happening right now, act on it fast, and trust the record afterward.

**Emotional goals:** Calm confidence. The interface should make the operator feel in control, not overwhelmed. It should disappear into the background and surface only what matters.

---

### Brand Personality

**Three words:** Trustworthy. Precise. Calm.

**Inspiration:** Linear — structured, confident, unfussy. Every element earns its place. No gradients, no chrome, no decorative noise. Typography-forward. Hierarchy through weight and spacing, not color.

**Anti-references:** Anything that looks like a SaaS startup dashboard (gradient cards, colorful stat tiles, rounded-everything). Anything that feels "exciting" — this product is used by people whose job requires focus, not delight.

**Logo:** FlytBase brand colors should be preserved. A greyscale logo variant is acceptable and encouraged where it better serves the neutral aesthetic.

---

### Aesthetic Direction

**Theme:** Dark. Non-negotiable — operators are in dark rooms on long shifts. Light mode is only relevant for compliance officer reports.

**Palette:** Neutral blacks and dark grays. Move away from the current cool-blue dominance. Color earns its place only as a semantic signal — status indicators (success/error/warning/caution) retain their meaning but should not dominate the visual field. No blue as a decorative or brand-expression color. FlytBase brand colors (logo) are preserved but used sparingly.

**Specific palette direction:**
- Backgrounds: near-true-blacks with subtle warm or neutral undertones (avoid cold steel-blue tints)
- Surfaces: layered dark grays with minimal border contrast — depth through tone, not outline
- Text hierarchy: three levels of opacity on off-white (primary, secondary, tertiary)
- Accent: reserved strictly for interactive elements (focus rings, active states, CTAs)
- Status colors: retained as semantic signals, muted slightly so they inform rather than alarm

**Typography:** Needs to move away from Inter/DM Sans (overused). Something that feels precise and editorial — closer to a technical instrument manual than a SaaS marketing page. Explore: Geist, Roobert, Neue Haas Grotesk, Aktiv Grotesk, or a well-chosen monospace/grotesque pairing.

---

### Accessibility

- **WCAG AA minimum everywhere.** WCAG AAA on all body text and critical status indicators.
- **Colorblindness mode:** A first-class toggle in Settings. At minimum: deuteranopia/protanopia support — replace hue-only distinctions (red/green) with shape + label + pattern combinations.
- **Reduced motion:** Respect `prefers-reduced-motion`. Animations should degrade gracefully to instant transitions.
- **Focus management:** All interactive elements must have visible, high-contrast focus rings. No outline: none without a substitute.
- **Text sizing:** Support system font size preferences. No fixed px for body text — use rem.

---

### Design Principles

1. **Scannable over beautiful.** A fatigued operator reads in milliseconds. Hierarchy must be immediate — size, weight, and position carry meaning before color does.

2. **Color means something.** In this product, color is a signal, not decoration. If it's red, something needs attention. If it's green, something is confirmed. Decorative color use is a liability.

3. **Earn every pixel.** Linear-style restraint: no element that doesn't carry information or enable an action. No decorative cards, no icon-above-heading templates, no visual chrome for its own sake.

4. **Quiet confidence.** The interface should feel like a precision instrument — not exciting, not anxious. Confident in its own clarity. When everything is calm, the alarm stands out.

5. **Accessibility as infrastructure.** WCAG AA/AAA compliance and colorblind mode are not features to add later — they are load-bearing constraints for every design decision.

## Linear Reference System (concrete specifics)

These are not brand values — they are craft standards. Where Verkos's brand context says "what," this section says "how," drawn from inspecting Linear, reading Karri Saarinen's published design principles, and Linear's public writing on Method and Invisible Details.

**Use this section as the tiebreaker when a design decision has ambiguity.** Every implementation choice should be able to justify itself against one of these specifics.

### Typography

- **Body / UI:** Inter. All body text, labels, inputs, rows, buttons.
- **Display:** Inter Display (the optical-size variant of Inter, designed for larger sizes). Use it only where text is ≥20px — page titles, large stat values, empty-state headings. Body text never uses Inter Display.
- **Monospace:** System mono stack (`ui-monospace, SFMono-Regular, Menlo, Consolas, monospace`). Use exclusively for: row IDs (`VRK-001`), code blocks, data readouts. Never for prose.
- **Tabular numbers:** Every numeric display must use `tabular-nums` (CSS `font-variant-numeric: tabular-nums`). Table numeric cells, sidebar badges, durations, counts, timestamps. Inter supports this via its OpenType feature.
- **Never:** italics in UI chrome (labels, buttons, nav). Reserve italics for in-prose quoted content only (pilot observations).

### Color approach

- **Neutrals are LCH/OKLCH-generated, slightly cool-tinted.** The faint blue cast in the dark surface ramp is intentional. Verkos preserves this but shifts toward neutral (per brand context: "move away from cool-blue dominance"). The tint should be almost imperceptible, not a visible blue cast.
- **Accent budget:** Maximum 1–2 accent-colored elements visible per screen. If you find yourself adding a third, something is wrong with the hierarchy.
- **The accent color is earned by the single most important action on the screen.** For Verkos: the Generate Report CTA in the wizard, the Create Report FAB until the top bar exists. Nothing else.
- **Status colors carry meaning, never decoration.** Critical = error-30, high = warning-30, moderate = caution-30, low = muted text (not success-30 green — green implies "good," which misrepresents low-severity findings).
- **Depth is tonal, not shadowed.** Surface elevation goes: `background` → `background-level-1` → `background-level-2` → `background-level-3`. Shadows appear only on floating surfaces (modals, popovers, menus) and are soft/low-opacity.
- **Borders are hairlines.** 1px max, using `outline-secondary` (quieter) or `outline-primary` (slightly firmer). Never use a border as decoration. If a surface needs to feel contained, lift it one level tonally first, add a border second.

### Spacing

- **4px base grid.** All padding and gap values must be multiples of 4: `gap-1` (4), `gap-2` (8), `gap-3` (12), `gap-4` (16), `gap-6` (24), `gap-8` (32). Never arbitrary values.
- **List row height target: 32–40px.** Use `py-2` on table rows. Generous row padding is the signature of an undesigned app.
- **Sidebar item height: 28–32px.** `py-1.5` with `fb-body-2` text.
- **Button height scale: 28 / 32 / 36px** (`py-1` / `py-1.5` / `py-2` with `fb-body-3` text). Matching input height critical for horizontal alignment.
- **Modal padding:** 24px body, 16–20px header. The panel itself is 480–640px wide.

### Radius

- **4px:** small pills, badges, inputs, buttons (`rounded` or `rounded-sm`)
- **6px:** rows, list items, cards (`rounded-md`)
- **8px:** modals, dialogs, large cards (`rounded-lg`)
- **Full radius is for true circles only:** avatars, the primary FAB. Never for pill-shaped badges — those are 4px.
- **Never exceed 8px** in UI chrome. Rounded-xl and rounded-2xl are marketing-page aesthetics and break the precision-instrument feel.

### Motion

- **Hover / focus transitions: 100–150ms.** Use `duration-150` as the default. `duration-200` is for larger surface changes (modal open, drawer slide).
- **Modal / menu enter: 150–200ms.**
- **Never exceed 250ms.** Long transitions feel sluggish in a control-room context.
- **Easing: `ease-out` for entrances, `ease-in` for exits.** Never bounce, never elastic, never spring on UI chrome. Spring physics reserved for drag/reorder interactions only.
- **Motion communicates state changes, not decoration.** If a transition doesn't tell the user something changed, remove it.
- **Respect `prefers-reduced-motion`** — collapse all transitions to 0ms duration for those users.

### Icons

- **Size: 16px in the product, 12px for inline tight contexts, 20px for empty states and empty headings.** Never size an icon larger than the text it sits beside.
- **Color: inherit from text.** Icons use `currentColor`. The only exception is status icons (severity dots), which carry meaning through color.
- **Stroke weight: 1.5px.** When using Font Awesome, prefer `fa-regular` or `fa-light` weights over `fa-solid` for chrome icons (navigation, secondary actions). Reserve `fa-solid` for status indicators and primary CTAs where weight matters.
- **Never use multi-color icons in UI.** No duotone, no gradient fills, no emoji as icons.

### Component patterns

- **Buttons:** Primary is solid accent (text-background on bg-primary). Secondary is neutral surface with hairline border. Ghost has no fill or border, reveals tint on hover. Destructive uses error color as text on neutral surface, filled only for irreversible actions.
- **Inputs:** 1px neutral border, transparent or `background-level-2` fill, 8–10px vertical padding. Focus replaces border with accent color + optional soft accent ring. No heavy box-shadow on focus.
- **Modals:** Centered, 8px radius, backdrop is ~50% opacity black with optional 8px backdrop blur. Not full glassmorphism.
- **Dropdowns / menus:** Elevated surface (`background-level-3` minimum), 6px radius, 4px inner padding. Item height 28–32px. Arrow-key navigation by default with highlight matching hover state.
- **Rows:** Entire row is hit target. Hover reveals 5–8% tint (`surface-hover`). Selection uses a stronger tint (`surface-selected`), never a colored left-edge stripe — that pattern is banned site-wide. Border-bottom hairline only; no vertical grid lines; no zebra striping.
- **Status / priority:** Colored dot (6–8px) followed by text in the row's neutral text color. Never a filled pill. Never background fill behind severity labels. The only exception is `Incident` type, which inherits `text-error-30` on its label to carry the urgency forward.
- **Empty states:** Do not use centered icons above text. Left-align. Explain what lives here, what produces it, what action creates one. Offer a direct action when appropriate.

### Interaction philosophy (the non-negotiables)

1. **Keyboard-first.** Every action must be reachable by keyboard. Future work should include a command palette (⌘K) as Linear does.
2. **Invisible details.** Craft reveals itself in moments users never consciously notice. A hover reveal that waits 50ms before appearing, a focus ring that arrives on the exact frame of the click, a modal that sizes itself to content with no layout flash. These are the difference between "works" and "feels right."
3. **Reduce scope to raise quality.** When in doubt, remove. A feature shipped at 80% quality is worse than a feature not shipped.
4. **Pixel-perfect is a mindset.** The implementation is the deliverable, not the mock. If a mock shows `margin-top: 24px` but the final layout needs 20px, ship 20px.
5. **Restraint in color and motion.** Both carry meaning. Both lose meaning when overused. When you want to add color or motion, try removing something first.

### What Verkos explicitly avoids (Linear-aligned)

- Filled pill status chips (`bg-* rounded-full px-2 py-0.5` on severity/status labels)
- Alternating zebra rows
- Box-shadow depth (use tonal levels)
- Spinners where skeletons would work
- Emoji in UI chrome
- Bounce / elastic easing
- Multi-color decorative icons
- Density toggles (density is opinionated, not configurable)
- `rounded-xl` or larger in product chrome
- Decorative gradients anywhere in the product (marketing pages are permitted different rules; product UI is not)
